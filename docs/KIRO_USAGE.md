## Property-based testing
- Lovers_Binding task 8.9: a Kiro spec-task subagent wrote `packages/grimoires/lovers-js/src/binding-parse.pbt.test.ts` — Property 13 (R17.1, R17.2). It drives the REAL pipeline (`extractPlan` -> `LocalLoversRunner` -> `validateLovers`) with a deterministic Mock `LlmPort` and asserts, over 300 generated bindable plans, that `pythonHeart`/`pythonTests` parse as Python 3 and `jsBeloved`/`jsTests` parse as JavaScript with zero error nodes, and that `contractSchema` is a valid contract. Writing the property surfaced a latent correctness bug the PBT exploration flagged: `extractPlan` marked a function bindable on JSON-serialisability alone, so a Python function or parameter named a JS reserved word (`delete`, `new`, `class`, …) made the bridge emit invalid JavaScript and silently forced a `path:"template"` fallback. Fixed by making the deterministic extractor the single source of bindability truth — it now refuses non-emittable JS identifiers with an oracle-voice `skipReason` (honouring "the cards cannot lie"), with new coven tests and the 8.8 generator hardened so its "never collides with a keyword" guarantee is actually true. lovers-js suite ran 3x green (8 files / 30 tests), flake gone.
- Lovers_Binding task 5.2: a Kiro spec-task subagent wrote `packages/coven/src/chunk/residual-chunk.pbt.test.ts` — Property 9 (R11.1, R11.2). A grammar-shaped generator of small py3 modules (>=2 top-level units) feeds the real `groupResiduals` + real oracle `parsePython`; 1000 runs assert every chunk `context` is a strict (proper) subset of the file, the chunks' residuals partition the input, and grouping is deterministic. 120/120 coven tests green.

### Nov 4, 2026 - Spec 02-github-summoner, task 1 (tar-stream spike)
- Verified `tar-stream@3.2.2` through the `Readable.fromWeb` bridge with committed characterization tests (`packages/github/src/tar-extract.spike.test.ts`): pax global (g) and extended (x) headers and GNU long names resolve into `header.name` and never surface as entries; traversal names pass through verbatim (our normalizer must reject them); destroying extract + bridge, or a byte-counting guard error placed before the bridge, cancels the upstream reader and stops pulling.
- Finding: the async-iterator form (`for await`) does not block on an unconsumed entry. `next()` auto-drains and discards it. Only the event form `extract.on("entry", (header, stream, next) => ...)` blocks until `stream.resume()` + `next()`.
- Decision: the extractor uses the event form with explicit `next()` (design D3). Byte-count guards sit upstream of tar-stream, so skipped-entry bytes count toward the caps (P11 groundwork tests, R3.10 and R3.11).
- Install note: `tar-stream@3.2.2` declares `bare-fs` (plus b4a, streamx, fast-fifo). We never call an fs path, but it enlarges the install footprint.
- Hook: `auto-commit-after-task` now runs `pnpm -r typecheck` and `pnpm -r test`. Added `test` scripts to `@necro/oracle` and `@necro/github`.
- Event-form hazard found while writing the skipped-bytes test: destroying `extract` with an error also errors the in-flight entry stream, and with no `error` listener that is an uncaught exception. Every entry handler in the real extractor must attach `stream.on("error", ...)`.

# Requirements Document

## Introduction

Lovers_Binding is the final additive layer of the Necro-Oracle. It adds four
cohesive capabilities without changing the behaviour of any prior spec
(`01-oracle-deck-engine`, `02-github-summoner`, `03-crt-terminal`,
`arcana-visions`, `fix-wasm-tracing`, `resurrection-engine`, `visual-necromancy`,
`oracle-landing-polish`). These requirements are derived from the approved
design document (`design.md`) and mirror the design's four parts plus a quality
bar.

- **Part A — OpenRouter LLM layer.** A real OpenRouter provider behind the
  existing `Llm_Port`, with a pure `Model_Router`, versioned prompt templates,
  strict structured output, usage/cost accounting, caching, timeouts, and
  budgets. The Mock provider stays the default network-free provider and
  unit/property tests never touch the network.
- **Part B — Resurrection LLM_Pass.** The existing runner's LLM_Pass is wired
  to send only residual diagnostics per chunk and to accept structured edits
  behind a deterministic validation gate, falling back to the deterministic
  result for any chunk that fails.
- **Part C — The Lovers (VI).** A new grimoire binds a Python 3 heart to a
  JavaScript beloved through a JSON contract, generated by an LLM
  plan-then-generate pipeline, validated by tree-sitter (Python + JavaScript),
  with a deterministic AST-template fallback, surfaced by a streaming route, a
  DMG split view, and a client-side ZIP download.
- **Part D — Bring Your Own Key (BYOK).** A no-persistence security feature:
  the user may supply their own OpenRouter key for the current browser tab
  only; it is transported per request in a dedicated header, used for that
  request's OpenRouter calls, and never stored, logged, cached, echoed, or
  included in the response cache key.

The governing rule is do no harm. New heavy code is lazy-loaded as distinct
chunks, `BUDGET_BYTES` stays `250000`, and the deck rule holds: deterministic
detectors and gates decide, while the LLM only interprets, narrates, and may
only downgrade.

This document specifies requirements only. Design and implementation live in
`design.md`.

## Glossary

- **Lovers_Binding**: The system under specification: the final additive layer
  adding the OpenRouter LLM layer, the Resurrection LLM_Pass refinement, The
  Lovers grimoire, and Bring Your Own Key.
- **Llm_Port**: The existing provider-port interface
  (`complete(req, opts?): Promise<LlmResult>`) through which runners obtain
  completions; `providerId` is one of `mock`, `bedrock`, `anthropic`, `openai`,
  or `openrouter`.
- **Mock_Provider**: The deterministic, network-free `Llm_Port` implementation
  used in tests and demo mode; it is the default provider.
- **OpenRouter_Provider**: The real `Llm_Port` implementation that calls the
  OpenRouter chat-completions endpoint over `fetch` with an `AbortController`
  timeout.
- **Model_Router**: The pure function `routeModel(signals): ModelTier` that
  selects a model tier from measurable signals.
- **Model_Router_Port**: The injected port exposing the pure `route(signals)`
  and `resolveModel(tier, override?)`, so `@necro/llm` never imports
  `@necro/coven`.
- **resolveModel**: The pure resolver mapping a Model_Tier (plus an optional
  BYOK/YOURS override) to a concrete model id, precedence override then the tier
  environment model.
- **Usage_Aggregate**: The reading-level fold of Usage_Records carrying total
  prompt tokens, completion tokens, cost, the Soul_Source, and a per-model
  breakdown.
- **Extract_Plan**: The deterministic tree-sitter extraction of the resurrected
  Python 3 source's top-level function names, parameters, and defaults, used as
  the PLAN context, the PLAN-failure fallback plan, and the fixture input.
- **Deny_List_Scan**: The pure static scan over generated code that rejects
  dangerous constructs (eval/Function/exec, network, filesystem writes/deletes,
  `os.system`, `child_process` beyond spawning the heart).
- **Model_Tier**: One of `FAST` or `STRONG`.
- **Router_Signals**: The pure input to the Model_Router: a token estimate, a
  count of unresolved diagnostics, and difficulty flags (metaclass,
  unicode-bytes, dynamic-import, cross-lang-type-mapping).
- **Prompt_Template**: A versioned template (role, rules, output schema name,
  few-shot examples) stamped with PROMPT_VERSION and keyed by purpose.
- **PROMPT_VERSION**: The constant stamping prompt templates and participating
  in every cache key so a template change invalidates cached completions.
- **Structured_Output**: A model response constrained to a strict JSON schema
  (`response_format` json_schema) with an extract-plus-zod fallback and one
  repair retry before deterministic fallback.
- **Usage_Record**: The pure value recording the model actually served, prompt
  tokens, completion tokens, and cost in USD for one call; `sumUsage` folds a
  list of Usage_Records into the Usage_Aggregate "souls spent" total (tokens +
  cost + per-model breakdown) with the Soul_Source held at the reading level.
- **Residual_Chunk**: A per-function or per-chunk unit grouping only that
  chunk's residual diagnostics plus the minimal referenced context, never the
  whole file.
- **Chunk_Edit**: The structured edit a model returns for a chunk
  (`{ chunkId, replacementCode, requiredImports, reason, confidence }`), where
  `requiredImports` are stdlib-only import lines the runner hoists
  deterministically outside the chunk and `confidence` 0 means decline.
- **Chunk_Gate**: The deterministic validation gate that decides whether a
  Chunk_Edit is accepted.
- **Lovers_Grimoire**: The new adapter-free grimoire that binds a Python 3
  heart to a JavaScript beloved for the `python3->javascript` language pair.
- **Lovers_Runner**: The coven runner that drives the Lovers pipeline
  (PLAN then GENERATE then VALIDATE then EMIT) using the injected Llm_Port.
- **Lovers_Plan**: The strict structured plan produced by the FAST model (the
  function list, the Python-to-JSON-to-JS type map, and edge cases).
- **Lovers_Pair**: The generated working pair: a deterministically-emitted
  Python 3 heart, an LLM-or-template JavaScript beloved, the JSON Schema
  contract, and contract tests for both sides. The GENERATE step's LLM output
  carries only the beloved, the contract, and the two tests; the heart is always
  emitted deterministically by the AST-template bridge.
- **Contract_Schema**: The JSON Schema draft 2020-12 document, serialized as a
  string, describing the values exchanged over the JSON-lines-over-stdin/stdout
  contract between the heart and the beloved, carrying exactly a
  `$defs["<fn>.request"]` and a `$defs["<fn>.response"]` entry per bindable
  function.
- **Lovers_View**: The lazily loaded DMG split-view screen (Python left,
  contract center, JavaScript right) plus the pixel ritual visuals.
- **Zip_Builder**: The lazily loaded client-side module that builds the
  downloadable ZIP (`python/`, `js/`, `contract/`, and a `README`).
- **Lovers_Route**: The streaming NDJSON route `POST /api/lovers` mirroring the
  resurrect route.
- **Language_Pair_Id**: The parameter identifying the source-to-target pair;
  today only `python3->javascript` is enabled.
- **Soul_Source**: The active key source for a request: `ORACLE` (the server
  key under daily ceilings) or `YOURS` (the user-supplied key).
- **Soul_Key_Container**: The in-memory-only container (a React ref) holding the
  user key for the current tab; it exposes operations, never the raw value as
  state.
- **User_Key_Header**: The dedicated per-request header `X-Necro-User-Key`
  carrying the user key to the resurrect and lovers routes only.
- **Model_Id_Pattern**: The safe model-id regular expression
  (`MODEL_ID_RE`) that a session model override must match.
- **Soul_Source_HUD**: The HUD indicator showing `SOUL SOURCE: ORACLE` or
  `SOUL SOURCE: YOURS` and the souls-spent attributed to the active source.
- **DMG_Palette**: The strict 4-shade palette `#001a00`, `#0b4f1a`, `#2fa84a`,
  `#8cff9e`.
- **Budget_Gate**: The `scripts/check-web-budget.mjs` check plus `budget.test.ts`
  that enforce `BUDGET_BYTES` and the distinct lazy chunks.
- **BUDGET_BYTES**: The pinned terminal-route initial JS budget, `250000` bytes
  gzipped.
- **Oracle_Voice**: The project narration style: one short mystical line, then
  the plain technical fact, ASCII-only, no emoji.

## Requirements

### Requirement 1: OpenRouter provider behind the Llm_Port

**User Story:** As an operator, I want a real OpenRouter provider behind the
existing Llm_Port, so that the oracle can call live models while the Mock
provider stays the default.

#### Acceptance Criteria

1. THE OpenRouter_Provider SHALL implement the Llm_Port interface with `providerId` equal to `openrouter`.
2. WHEN the OpenRouter_Provider completes a request, THE OpenRouter_Provider SHALL send an OpenAI-compatible chat-completions request to the OpenRouter endpoint over `fetch`.
3. WHEN the OpenRouter_Provider sends a request, THE OpenRouter_Provider SHALL include the headers `Authorization: Bearer <key>`, `Content-Type: application/json`, `HTTP-Referer`, and `X-Title: Necro-Oracle`.
4. WHEN the OpenRouter_Provider sends a request, THE OpenRouter_Provider SHALL arm an `AbortController` so the request aborts after the request's timeout in milliseconds elapses.
5. WHEN the OpenRouter_Provider receives a successful response, THE OpenRouter_Provider SHALL return an `LlmResult` carrying the completion text and a Usage_Record with prompt tokens, completion tokens, and cost.
6. IF the OpenRouter endpoint returns a timeout or abort, THEN THE OpenRouter_Provider SHALL return a typed `NETWORK_TIMEOUT` error.
7. IF the OpenRouter endpoint returns a server or network failure other than `401` or `402`, THEN THE OpenRouter_Provider SHALL return a typed `UPSTREAM_UNAVAILABLE` error.
8. THE Mock_Provider SHALL remain the default provider and SHALL require no network access.

### Requirement 2: OpenRouter configuration via environment variables

**User Story:** As an operator, I want model selection and keys to come from
validated environment variables, so that model ids stay configuration and
secrets are never printed.

#### Acceptance Criteria

1. THE Lovers_Binding configuration SHALL read `OPENROUTER_API_KEY`, `NECRO_LLM_MODEL_FAST`, `NECRO_LLM_MODEL_STRONG`, and `NECRO_LLM_MODEL_FALLBACKS` from validated environment variables.
2. WHEN `NECRO_LLM_MODEL_FALLBACKS` is provided as a comma-separated list, THE Lovers_Binding configuration SHALL transform it into an array of model ids.
3. IF `OPENROUTER_API_KEY` is present, THEN THE Lovers_Binding composition SHALL build the OpenRouter_Provider.
4. IF `OPENROUTER_API_KEY` is absent, THEN THE Lovers_Binding composition SHALL keep the Mock_Provider as the default provider, except that a request carrying a valid user key SHALL build the OpenRouter_Provider per request from that user key (Requirement 24.2).
5. THE Lovers_Binding configuration SHALL treat each model id as configuration with its default documented only in `docs/PROMPTS.md` and never hardcoded in product code.
6. WHEN the OpenRouter_Provider sends a request with configured fallback model ids, THE OpenRouter_Provider SHALL include the OpenRouter `models` fallback array built from `NECRO_LLM_MODEL_FALLBACKS`.
7. IF environment validation fails, THEN THE Lovers_Binding configuration SHALL report an error that names only the offending keys and never a secret value.

### Requirement 3: Pure Model_Router

**User Story:** As a maintainer, I want model-tier selection to be a pure
deterministic function of measurable signals, so that routing is predictable
and testable without a network.

#### Acceptance Criteria

1. THE Model_Router SHALL select exactly one Model_Tier from the Router_Signals with no side effects.
2. IF any difficulty flag among metaclass, unicode-bytes, dynamic-import, or cross-lang-type-mapping is set, THEN THE Model_Router SHALL return `STRONG`.
3. IF the count of unresolved diagnostics exceeds the FAST diagnostic limit, THEN THE Model_Router SHALL return `STRONG`.
4. IF the token estimate exceeds the FAST token limit, THEN THE Model_Router SHALL return `STRONG`.
5. WHILE no difficulty flag is set AND the unresolved-diagnostics count and token estimate are within their FAST limits (FAST diagnostic limit 6, FAST token limit 1200), THE Model_Router SHALL return `FAST`.
6. THE Model_Router signal extraction SHALL derive the difficulty flags by pure inspection of the minimal context with no model call and no network access.
7. WHEN routing a Lovers GENERATE unit, THE Model_Router SHALL route by function count and token estimate rather than forcing `STRONG` for every GENERATE, so the cross-lang-type-mapping flag informs the PLAN difficulty but does not by itself force GENERATE to `STRONG`.

### Requirement 4: One unified retry policy for every LLM unit

**User Story:** As a maintainer, I want every LLM unit to obey one retry policy,
so that a failed attempt retries exactly once on a stronger model and then falls
back deterministically, with a hard cap on calls.

#### Acceptance Criteria

1. WHEN any LLM unit (a Resurrection chunk, a Lovers PLAN, or a Lovers GENERATE) fails its zod schema OR its validation gate, THE Lovers_Binding runner SHALL issue exactly one retry carrying the exact error string.
2. WHEN a unit started at `FAST` and is retried, THE Lovers_Binding runner SHALL run the retry at `STRONG`; WHILE a unit started at `STRONG`, THE Lovers_Binding runner SHALL keep the retry at `STRONG` and SHALL never downgrade it to `FAST`.
3. IF the single retry still fails, THEN THE Lovers_Binding runner SHALL run the deterministic fallback and SHALL NOT throw.
4. THE Lovers_Binding runner SHALL make at most two model calls per unit (MAX CALLS PER UNIT = 2).

### Requirement 5: Token economy and caching

**User Story:** As an operator, I want tight token usage and content-hash
caching, so that completions stay cheap and repeatable.

#### Acceptance Criteria

1. WHEN the Lovers_Binding runner builds a request, THE Lovers_Binding runner SHALL supply a minimal AST-sliced context limited to the target unit plus referenced signatures and imports.
2. WHEN the Lovers_Binding runner builds a request, THE Lovers_Binding runner SHALL place a stable system prompt first, set a bounded `max_tokens` derived from the input size, and set temperature to exactly 0 for every purpose.
3. THE Lovers_Binding completion cache key SHALL equal the hash of the purpose/template id, schema name, PROMPT_VERSION, resolved model id, content hash, and the retry-flag or error hash, and SHALL never include the user key.
4. WHEN two requests share an identical cache key, THE Lovers_Binding completion cache SHALL return the cached result and mark it cached.
5. THE Lovers_Binding runner SHALL record a Usage_Record for each completion with prompt tokens, completion tokens, cost, and the model actually served.
6. THE Lovers_Binding completion cache SHALL store only outputs that passed both the zod schema and the validation gate.

### Requirement 6: Usage and cost accounting fold

**User Story:** As a user, I want a sound "souls spent" total, so that the cost
of a reading is reported accurately.

#### Acceptance Criteria

1. THE Usage_Record aggregation `sumUsage` SHALL be associative and commutative over the token and cost fields.
2. THE Usage_Record aggregation `sumUsage` SHALL yield non-negative totals for prompt tokens, completion tokens, and cost.
3. THE Usage_Record aggregation `sumUsage` SHALL carry a per-model breakdown whose per-model token and cost sums equal the aggregate totals, and SHALL keep the Soul_Source at the reading level.

### Requirement 7: Strict structured output with repair-once fallback

**User Story:** As a maintainer, I want structured model output validated
strictly with a single repair retry, so that malformed output never breaks the
pipeline and never throws.

#### Acceptance Criteria

1. WHEN the OpenRouter_Provider requests Structured_Output AND the model supports it, THE OpenRouter_Provider SHALL send `response_format` as a strict `json_schema` generated from the output zod schema.
2. IF the model lacks json_schema support, THEN THE Structured_Output parser SHALL extract the first balanced JSON object from the response text and validate it against the output zod schema.
3. WHEN Structured_Output fails validation, THE Lovers_Binding runner SHALL apply the one unified retry policy of Requirement 4 (exactly one retry carrying the exact validation error, escalating FAST to STRONG) rather than a separate retry.
4. IF the single retry still fails validation, THEN THE Lovers_Binding runner SHALL fall back to the deterministic layer and SHALL NOT throw.

### Requirement 8: Versioned prompt templates and prompt-injection defense

**User Story:** As a maintainer, I want versioned prompt templates that treat
repository code as untrusted data, so that prompt injection inside repository
code is ignored and template changes invalidate the cache.

#### Acceptance Criteria

1. THE Prompt_Template catalogue SHALL stamp every template with PROMPT_VERSION and SHALL include a role, explicit rules, the output JSON schema name, and one or two few-shot examples.
2. WHEN a Prompt_Template embeds repository source, THE Prompt_Template SHALL neutralise any literal occurrence of the untrusted-open or untrusted-close marker inside the source, wrap the source between the fixed untrusted delimiters so the built request has exactly one opening and one closing marker, and label the delimited span as data to be ignored as instructions.
3. WHEN repository source inside the untrusted delimiters contains an instruction that would introduce disallowed code, THE Lovers_Binding runner SHALL reject the resulting output at the schema, gate, or deny-list before acceptance so the injected instruction never takes effect.
4. WHEN PROMPT_VERSION changes, THE Lovers_Binding completion cache SHALL treat prior cached completions as invalid because the cache key includes PROMPT_VERSION.

### Requirement 9: Safety, cost ceilings, and secret hygiene for the LLM layer

**User Story:** As an operator, I want reused budgets, ceilings, and strict
secret hygiene, so that spend is bounded and no secret, prompt, or code body is
ever logged.

#### Acceptance Criteria

1. THE OpenRouter_Provider SHALL reuse the existing budget, cache, and spend-breaker infrastructure and SHALL apply a per-request token cap and a daily request ceiling from `NECRO_LLM_DAILY_CEILING`.
2. THE OpenRouter_Provider log output and the returned `LlmResult` SHALL contain no API key, no prompt body, and no code body, and SHALL contain only identifiers, sizes, token counts, and cost.
3. WHEN the OpenRouter_Provider completes a request, THE OpenRouter_Provider SHALL reuse the shared completion cache so the cached flag behaves identically to the Mock_Provider.

### Requirement 10: LLM layer tests never touch the network

**User Story:** As a maintainer, I want the LLM layer to be fully testable
offline, so that unit and property tests never open a socket.

#### Acceptance Criteria

1. THE OpenRouter_Provider SHALL accept an injectable fetch implementation so tests drive it with recorded golden fixtures keyed per PROMPT_VERSION.
2. THE no-network guard's guarded files SHALL import no network module, and the OpenRouter_Provider SHALL live outside the guarded file set.
3. WHILE running unit or property tests, THE Lovers_Binding test suite SHALL reach the OpenRouter_Provider only through an injected fetch implementation and never open a network socket.

### Requirement 11: Residual chunking for the Resurrection LLM_Pass

**User Story:** As a maintainer, I want the LLM_Pass to receive only residual
diagnostics per chunk, so that the model never sees the whole file.

#### Acceptance Criteria

1. WHEN the LLM_Pass groups residuals, THE residual grouping SHALL produce Residual_Chunks each carrying only that chunk's diagnostics.
2. THE residual grouping SHALL set each Residual_Chunk context to a strict subset of the file consisting of the enclosing function or class plus referenced signature and import lines, and SHALL never emit the whole file.
3. THE residual grouping SHALL be a pure function of the path, source, and residual set with no side effects.

### Requirement 12: Chunk validation gate for structured edits

**User Story:** As a maintainer, I want every chunk edit to pass a deterministic
gate before acceptance, so that the LLM can only improve a chunk and never
worsen it.

#### Acceptance Criteria

1. THE LLM_Pass SHALL require each chunk edit to be the structured shape `{ chunkId, replacementCode, requiredImports, reason, confidence }` validated against the strict zod schema, where the `py2to3.chunk` purpose produces the edit.
2. WHEN a chunk edit is evaluated, THE Chunk_Gate SHALL accept the edit only if the spliced result parses as Python 3 with zero error nodes, retains no Python 2 constructs under the reused diagnosis rules, preserves public signatures, and keeps the diff within that chunk, excluding the deterministically hoisted `requiredImports` from the diff-within-chunk check.
3. IF a chunk edit fails the Chunk_Gate, THEN THE LLM_Pass SHALL apply the one unified retry policy of Requirement 4 (exactly one retry carrying the exact failure reason, escalating FAST to STRONG) and SHALL then keep the deterministic version for that chunk.
4. FOR ALL files, THE LLM_Pass output SHALL be at least as valid as the deterministic Pre_Pass result, with no additional Python 2 constructs and no parse regression.
5. THE LLM_Pass SHALL hoist the chunk edit's `requiredImports` deterministically outside the chunk, SHALL accept only stdlib import lines, and SHALL reject any `requiredImports` entry that is not a stdlib import line.
6. IF a chunk edit's `confidence` equals 0, THEN THE LLM_Pass SHALL treat it as a decline and keep the deterministic chunk with no retry.
7. IF a chunk edit's `replacementCode` contains a mask placeholder, THEN THE LLM_Pass SHALL reject the edit so a masked span is never written back into the source.

### Requirement 13: Healer attribution and souls spent for resurrection

**User Story:** As a user, I want to see which chunks the AI healed versus the
rules and the souls spent, so that resurrection stays honest and legible in
oracle voice.

#### Acceptance Criteria

1. WHEN the LLM_Pass completes, THE Resurrection result SHALL report, in Oracle_Voice, which chunks were healed by the LLM and which by the deterministic rules, together with each change's reason.
2. WHEN the LLM_Pass completes, THE Resurrection result SHALL report the souls spent as the aggregate Usage_Record of tokens and cost for the reading.
3. WHILE in demo mode, THE Resurrection LLM_Pass SHALL use the Mock_Provider.
4. THE Resurrection LLM_Pass SHALL leave the public `RitualResult` and `FileResult` shapes unchanged.

### Requirement 14: The Lovers command, chip, and precondition

**User Story:** As a user who drew The Lovers, I want a `lovers <file> js`
command and chip, so that I can bind a resurrectable file to a JavaScript
beloved, with a clear oracle-voice error otherwise.

#### Acceptance Criteria

1. WHEN the input `lovers <file> <lang>` is parsed with exactly two arguments AND `<lang>` is `js` or `javascript`, THE command parser SHALL produce a `lovers` command with `targetLang` normalized to `javascript` and the file preserved in its original case.
2. IF the input `lovers` is parsed with a target language other than `js` or `javascript`, THEN THE command parser SHALL produce an unknown command so the terminal shows an Oracle_Voice error.
3. WHILE The Lovers (VI) was drawn AND the file is resurrectable, THE Terminal SHALL offer the `lovers <file> js` command and its clickable chip and hint.
4. IF The Lovers (VI) was not drawn OR the file has no bindable top-level functions, THEN THE Lovers_Route SHALL terminate with a typed `VALIDATION_FAILED` Oracle_Voice error and SHALL NOT call a model.

### Requirement 15: Lovers LLM plan-then-generate pipeline

**User Story:** As a user, I want an LLM-first two-step pipeline that plans then
generates the pair, so that the binding is grounded in an explicit plan.

#### Acceptance Criteria

1. WHEN the Lovers_Runner runs the PLAN phase, THE Lovers_Runner SHALL request a strict Lovers_Plan from the FAST model containing the function list, the Python-to-JSON-to-JS type map, and edge cases.
2. WHEN the Lovers_Runner runs the GENERATE phase, THE Lovers_Runner SHALL request a strict Lovers_Pair from the routed model.
3. WHEN a PLAN or GENERATE response fails its strict schema or its validation gate, THE Lovers_Runner SHALL apply the one unified retry policy of Requirement 4 (exactly one retry carrying the exact validation error, escalating FAST to STRONG).
4. WHILE in demo mode, THE Lovers_Runner SHALL use the Mock_Provider with a pinned fixture so the demo path is deterministic and offline.
5. WHEN the Lovers_Runner runs the PLAN phase, THE Lovers_Runner SHALL send only the deterministic extracted plan of the resurrected source as the minimal context, and IF the PLAN phase fails after its single retry, THEN THE Lovers_Runner SHALL use that deterministic extracted plan as the fallback plan.

### Requirement 16: Lovers working pair and JSON contract

**User Story:** As a user, I want a working Python-to-JavaScript pair bound by a
JSON contract, so that the heart and the beloved interoperate.

#### Acceptance Criteria

1. THE Lovers_Binding SHALL take the resurrected Python 3 source of the file as the Lovers input and SHALL NOT take raw Python 2 as the input.
2. THE Lovers_Pair SHALL include a Python 3 heart that exposes at most eight selected top-level functions over a JSON-lines-over-stdin/stdout dispatcher, where one UTF-8 JSON object per line of the form `{"id": int, "fn": str, "args": {paramName: value}}` arrives on stdin and one line per response of the form `{"id", "ok": true, "value"}` or `{"id", "ok": false, "error": {"type": str, "message": str}}` is written on stdout.
3. THE Lovers_Pair SHALL include a JavaScript Node ESM beloved that is a client which spawns `process.env.PYTHON ?? "python3"` with `heart.py` as one long-lived child, correlates responses by `id`, exposes a `close()`, and calls the bound functions over the JSON contract with JSDoc types and input validation derived from the plan's edge cases, and SHALL NOT reimplement the Python logic in JavaScript.
4. THE Lovers_Pair SHALL include a Contract_Schema expressed as a JSON Schema draft 2020-12 document serialized as a string with exactly a `$defs["<fn>.request"]` and a `$defs["<fn>.response"]` entry per bindable function and nothing else, a Python-side contract test using `unittest` that calls the heart's `handle(request)` directly, and a JavaScript-side contract test using `node:test` and `node:assert`, with no third-party package, network, time, or randomness.
5. FOR ALL values in the Contract_Schema domain, a JavaScript round-trip validating the value against the Contract_Schema with `ajv` and decoding it SHALL yield the original value, and an optional continuous-integration-only Python round-trip SHALL run the same check and SHALL be skipped when `python3` is absent.
6. THE GENERATE step output SHALL contain only the JavaScript beloved, the Contract_Schema, the Python test, and the JavaScript test and SHALL NOT contain the Python heart, and THE Python heart SHALL be emitted deterministically by the AST-template bridge on both the LLM path and the fallback path and serialized with `json.dumps(..., ensure_ascii=False, allow_nan=False, separators=(",", ":"))` flushing after each line while redirecting the user function's stdout to stderr during a call and exiting 0 on end of input.

### Requirement 17: Lovers validation gate with tree-sitter and fallback

**User Story:** As a maintainer, I want the generated pair validated by
tree-sitter and the contract, with a deterministic fallback, so that an accepted
binding is proven and a failed one still produces a working pair.

#### Acceptance Criteria

1. WHEN the Lovers_Runner runs the VALIDATE phase, THE Lovers validation SHALL require the Python heart and the Python contract test to parse with zero error nodes using the Python grammar, and the JavaScript beloved and the JavaScript contract test to parse with zero error nodes using the JavaScript grammar.
2. WHEN the Lovers_Runner runs the VALIDATE phase, THE Lovers validation SHALL require the Contract_Schema to be a valid JSON Schema whose `$defs` keys (read as `<fn>.request` and `<fn>.response` and reduced to function names) equal the Lovers_Plan function names.
3. WHEN the Lovers_Runner runs the VALIDATE phase, THE Lovers validation SHALL require every function in the Lovers_Plan to be defined on both the Python heart and the JavaScript beloved.
4. IF validation fails after the single retry of Requirement 4, THEN THE Lovers_Runner SHALL fall back to the deterministic AST-template bridge and set the result path to `template`.
7. WHEN the Lovers_Runner runs the VALIDATE phase, THE Lovers validation SHALL run a static deny-list scan over every generated artifact and SHALL reject any pair that uses `eval`, `Function`, `exec`, `os.system`, network access, filesystem writes or deletes, or `child_process` other than spawning the Python heart.
8. IF the deny-list scan finds a forbidden construct, THEN THE Lovers_Runner SHALL reject the pair and SHALL apply the retry-or-fallback of Requirement 4 without executing the generated code.
5. WHEN validation passes, THE Lovers_Runner SHALL set the result path to `llm`.
6. THE Lovers_Result SHALL report which path was used.

### Requirement 18: JavaScript grammar traced identically to Python

**User Story:** As a maintainer, I want the JavaScript grammar WASM traced into
the lovers route exactly as the Python grammar is traced, so that parsing works
in the deployed route.

#### Acceptance Criteria

1. THE oracle core SHALL provide a `parseJavascript(source)` function that loads the JavaScript grammar WASM the same way `parsePython` loads the Python grammar, with the same parser arming and error-node counting.
2. THE web bundle tracing SHALL add the JavaScript grammar WASM specifier and SHALL add `/api/lovers` to the WASM include map alongside `/api/readings` and `/api/resurrect`.
3. THE WASM trace check SHALL assert the JavaScript grammar WASM is traced into `/api/lovers`.

### Requirement 19: Lovers streaming route

**User Story:** As a user, I want the lovers ritual to stream over NDJSON like
resurrect, so that progress and the result arrive with the same safety
guarantees.

#### Acceptance Criteria

1. THE Lovers_Route SHALL stream `application/x-ndjson` from inside the stream start and SHALL validate every line against the stream schema before writing.
2. THE Lovers_Route SHALL reuse the per-IP rate limiter chain and the WASM tracing used by the resurrect route.
3. THE Lovers_Route SHALL validate the request body against the strict `LoversRequestSchema` with fields `ref`, `file`, `targetLang`, `spread`, and an optional `demo`.
4. THE Lovers_Route SHALL log only `{ code, message, stack }` and SHALL never log a request body, token, or environment value.
5. WHEN a coven error reaches the Lovers_Route, THE Lovers_Route SHALL map it to an Oracle_Voice oracle code before the line is validated against the stream schema.

### Requirement 20: Lovers separate daily ceiling

**User Story:** As an operator, I want a separate lovers daily ceiling, so that
lovers spend on the server key is bounded independently.

#### Acceptance Criteria
